# Setup and operations

## Requirements and development

Use Node.js 22.13 or later and pnpm 11.25.0. Node 22's built-in `node:sqlite` module is currently experimental in that Node line; run the checked-in tests against the pinned runtime and review Node changes before upgrades. From the repository root:

```sh
pnpm install --frozen-lockfile
pnpm preflight
pnpm dev
```

The development server listens on `0.0.0.0:3000` for Webdev Preview. Express and Vite share that Node HTTP server; the Vite HMR WebSocket therefore travels through the configured Preview port. `BAYORA_DATABASE_PATH` is read only by the server; if absent, the default store is `data/bayora.sqlite` under the project root. The `data/` directory and SQLite/journal files are ignored by Git. `.env.example` contains no credential; an optional `.env` file is loaded on startup and must remain local/untracked.

The API executes only fixed scenario IDs. `GET /api/health` reports a query against the actual store, schema version and current row count. `POST /api/runs` accepts exactly `{"scenarioId":"<one of the three built-in IDs>"}`. `POST /api/runs/suite` accepts no body and atomically writes all three fixed results. `GET /api/runs?limit=100` lists up to 500 recent rows and the total, and `GET /api/runs/<id>` returns one record. Arbitrary prompt, dataset, tool, model, or target inputs are rejected. No model is called. The records are still synthetic, unsigned, unverified, unreviewed and unevaluated.

The API has a 16 KiB JSON parser limit, validates scenario IDs and list limits, has a process-local default limit of 60 run/suite writes per minute, and stops at 5,000 retained rows. Rate-limit and capacity errors are explicit and no rows are automatically deleted. The limiter is not distributed, user-specific abuse protection. The endpoints are unauthenticated and intended only for the specified fixed synthetic workflow on a trusted development/self-hosted node; do not expose them as a public general-purpose service.

## Database persistence and recovery

The BAYORA SQLite store is separate from Phoenix. Its schema version is maintained with SQLite `user_version`; startup creates the initial schema. It holds only fixed built-in synthetic records generated by the server. `data/bayora.sqlite` persists across an application restart only if its containing filesystem/volume is itself persistent and the instance is the same single node. It is not a shared database for multiple application instances. Do not use ephemeral multi-instance hosting and claim durable history. Development and published containers have separate files unless the operator configures an appropriate persistent volume; no volume has been configured in this project.

To take a basic local backup, gracefully stop BAYORA with `Ctrl+C`, wait for process exit, then copy the configured `.sqlite` file to an operator-controlled backup location. Do not copy/restore/delete an open database or its journal files. To restore, stop BAYORA, preserve a copy of the current database first, then place the chosen backup at the configured path and restart. This procedure is not an automated or tested backup service and does not provide off-site retention. Do not erase a database to fix a startup or migration problem.

## Checks and production-mode verification

```sh
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm production-smoke
```

`pnpm build` checks TypeScript, emits the compiled server under `dist/server` and builds browser assets under `dist/client`. `pnpm production-smoke` launches the compiled Node server against a unique temporary SQLite database/port, tests health/schema, client loading and server run creation, then removes only that isolated temporary test directory. To launch the built production server manually, run `NODE_ENV=production pnpm start`; it honors `PORT` (default `3000`) and the optional `BAYORA_DATABASE_PATH`. Always choose a persistent local volume before expecting records to survive a host replacement.

In dev mode, the `tsx` watcher reloads code changes. Stop cleanly with `Ctrl+C`; SIGTERM is also handled. No command removes the application's run history. This prototype has no approved public deployment target and is not production-ready.

## Phoenix upstream (separate service)

BAYORA reads `PHOENIX_BASE_URL` only in server configuration and calls only `/healthz`. For a separate local Phoenix instance, use `PHOENIX_BASE_URL=http://127.0.0.1:6006`; confirm its health at `curl -i http://127.0.0.1:6006/healthz`. A health response does not prove database readiness, identity, traces, datasets or evaluation access. Protected data endpoints remain blocked, and BAYORA neither installs/starts Phoenix nor shares its database.

The exact Phoenix source documents SQLite and PostgreSQL for its own service, and `PHOENIX_ENABLE_AUTH` defaults to false at the verified commit. Configure the upstream authentication/security boundary before exposing it to a network. Do not disable authentication to obtain a green health card. Real protected integration remains blocked without an authorized service and tested caller identity.

## Troubleshooting

- If Node cannot import `node:sqlite`, verify Node is at least 22.13.0. Do not replace the store or alter database state without reviewing the versioned schema first.
- If the app does not start, inspect the first error and verify the configured database directory is writable and `PORT` is an integer in the 1024–65535 range. Preserve existing DB files while troubleshooting.
- If Preview stays on its placeholder, confirm BAYORA logs port `3000` and fetch `/api/health` on the Preview origin.
- If Vite reports `WebSocket closed without opened`, keep Vite's HMR on the Express HTTP server at the configured Preview port; never expose a separate fallback HMR port.
- If Phoenix shows `Not configured`, set `PHOENIX_BASE_URL` in an ignored server-side `.env` and restart. `blocked` or `unavailable` describes the health probe only; no protected data was requested.
- If history appears truncated, the UI loads the latest 500 rows and identifies that limitation. Use the configured DB file with suitable operator-controlled read-only tools; do not reset it. At 5,000 rows, new writes fail explicitly and no retention/deletion is automatic.
- If the route manifest is stale, compare `public/manus-routes.json` with `src/client/App.tsx` and run `pnpm preflight`.
