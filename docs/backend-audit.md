# BAYORA pre-implementation audit and current capability matrix

> The first matrix is a historical pre-implementation snapshot dated 2026-10-27. Six independent subsystem reviewers performed read-only source reviews, followed by one synthesis reviewer. Its conclusion, statuses and gap list are superseded by the current implementation matrix near the end of this document; they are retained to preserve the original audit baseline.

## Pre-implementation conclusion (historical; superseded below)

BAYORA at that historical audit point was a prototype with a health-only Express surface, browser-executed fixtures and localStorage runs. It did not have the server run API, SQLite persistence, compiled production server or CI described in the current matrix. Its recorded 19 tests applied only to that pre-implementation version. Those findings drove the subsequent implementation; do not use them as current status.

## Cross-cutting gaps found at the pre-implementation audit (historical)

- No backend API creates, executes, retrieves, or authorizes runs; local fixture execution is browser-side only.
- No BAYORA server database, schema, migrations, durable/shared record history, backup, or recovery exists; localStorage is editable and browser-scoped.
- No server-validated identity or authorization exists, and no regression tests establish a future access policy.
- No BAYORA Phoenix data client/routes exist for traces, projects, datasets, experiments, evaluations, or reports; health-only status is not data integration or database readiness.
- No end-to-end UI/browser tests, UI-to-API orchestration tests, real Phoenix integration tests, or production-launch tests are recorded.
- No trusted evidence pipeline exists: signatures, verification, report export, protected review, and acceptance are absent; local run metadata is not proof.
- The local storage writer/reader size mismatch can hide all history above 5,000 records; EnvironmentPage can remain CHECKING for successful non-ok health JSON.
- No tracked CI workflow exists. The client build does not compile/package a server, and tsx is a development dependency used by the documented start script.
- No dedicated production secrets-management/rotation setup is established; the Phoenix URL is unconfigured in the audited environment.
- Phoenix's upstream ELv2 hosted-service restriction and BAYORA's undeclared original-code license require deployment/distribution review.

## External blockers at the pre-implementation audit (some remain; see the current matrix)

- No authorized, reachable Phoenix service URL/account is configured or available for verification; the audited live smoke was not_configured.
- A supported identity provider and approved server-side identity/authorization design are prerequisites for protected Phoenix and BAYORA operations. Until implemented and tested, protected actions must remain unavailable.
- Trusted signing and acceptance require authorized signing keys and a protected independent human-review process, neither of which is available in the audited state.
- A production deployment target and approved secret-injection mechanism are unspecified; production configuration and deployment behavior cannot be validated without them.
- Any future hosted/managed Phoenix deployment must account for Phoenix's ELv2 terms and obtain an explicit BAYORA licensing/distribution decision.

## Safe follow-up order from the pre-implementation audit

1. Preserve the current fail-closed boundary: do not add or expose protected data actions, bypass Phoenix controls, or treat health/build results as authorization or readiness.
2. Resolve governance and prerequisites first: approve the Phoenix deployment/use model under ELv2, identify an authorized reachable service, select a supported identity provider, and document roles, scopes, data boundaries, and secret handling.
3. Design and implement server-side identity validation and authorization middleware before protected routes; deny by default and add positive, negative, expired-identity, and cross-user authorization tests.
4. Implement durable BAYORA persistence with schema/migrations, ownership boundaries, retention, backup/recovery, and migration/restart tests; separately define whether Phoenix remains the upstream system of record.
5. Only after the identity/access gate passes, implement minimal server-side Phoenix clients for explicitly authorized operations, starting with read-only scope; validate schemas, timeouts, error handling, and access denial against a provisioned non-production service.
6. Add backend run lifecycle and UI-to-API workflows with provenance linking synthetic fixtures versus real Phoenix-derived data; keep the labels and stores clearly distinct, and never promote fixture results to real evaluations.
7. Implement report provenance, cryptographic signing/verification, and independent reviewer/acceptance workflows only after trusted identities, key custody, and protected review controls exist.
8. Fix the confirmed 5,000-record writer/loader mismatch and EnvironmentPage non-ok health state; add boundary and component tests.
9. Complete deployable server packaging, production-only install/start checks, graceful-shutdown tests, secret injection, and CI before claiming production readiness.
10. Run end-to-end authorization and data-flow tests against the approved service and document exactly what was exercised; keep all unverified upstream/runtime claims explicit.
